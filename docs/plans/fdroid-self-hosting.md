# Plan: self-hosted F-Droid repo for Notif APKs

Status: proposal, 2026-10-06, planning only. The Health Connect exporter that motivates the Android build is planned separately.

## Goal

Luka's phone installs and updates Notif through the stock F-Droid client, pointed at a self-hosted
repo that the VPS signs and serves. Nothing is submitted to f-droid.org; F-Droid is only the update
GUI. The repo is unlisted but not access-controlled: the fingerprint authenticates the repo, but does
not restrict who downloads from it (Q10). Done means one manual trigger yields a signed APK in the
repo, and the phone offers the update on its next refresh.

## Options

**O1. Where the APK is built and signed.** GHA = GitHub Actions. The build and time numbers are inference.

| | A. Build on the VPS | B. GHA builds on demand; VPS pulls, signs, publishes | C. GHA builds and pushes to the VPS over SSH | D. GHA builds and signs using secrets |
|---|---|---|---|---|
| VPS load per build | 3-5 GB RAM, 3 vCPU, 5-15 min, next to production | <0.5 GB, under 1 min | same as B | none (static upload) |
| Extra VPS disk | 4-6 GB (NDK, Gradle and pub caches) | about 1 GB (signer image) | about 1 GB | about 0 |
| Wall time | 4-10 min warm, 10-20 min cold | 3-8 min, plus about 1 min to publish | same as B | same as B |
| Where third-party build code runs (pub packages, Gradle plugins) | on the production host, in a container | GitHub's throwaway VM | GitHub's VM | GitHub's VM, in the same job as the keys |
| Who can reach the keys | VPS root | VPS root | VPS root, plus whoever holds the SSH key stored in GitHub | every step, action and Gradle plugin in the job |
| New credential | none | a read-only fine-grained PAT (personal access token) on the VPS | an SSH key in GitHub secrets | both keys in GitHub secrets |
| Moving parts | build image, cache volumes, resource caps | workflow, PAT, fetch-and-publish script | workflow, forced-command SSH, inbox watcher | workflow, secrets, upload step |
| Depends on GitHub | no | yes (A is the fallback) | yes | yes |
| Cost | 0 | 0 for a public repo | 0 | 0 |

**O2. Repo hostname.** `repo_url` must end in `/repo` and is how the client identifies the repo ([fds] config).

| | `https://fdroid.lcenzo.com/repo` | `https://notif.lcenzo.com/fdroid/repo` |
|---|---|---|
| Setup | one DNS record, plus one Caddy block that reuses the origin cert | one `handle_path`, placed before the SPA fallback |
| Isolation | its own cache headers and logs; no origin shared with the app | shares an origin and HSTS with the logged-in web app. A missing file must return 404 rather than fall through to `try_files ... /index.html`, which would answer 200 with HTML |
| More apps later (AGENTS.md lists "F-Droid hosted for app updates") | a neutral home | the URL is branded Notif |

**O3. Where versionCode comes from.**

| Source | Always increases | Same commit gives the same code | Manual step |
|---|---|---|---|
| `+N` in `pubspec.yaml`, bumped by hand | only if remembered | yes | every release |
| `git rev-list --count <sha>` on master (606 today) | yes, as long as master is never rewritten | yes | none |
| UTC timestamp, or a counter file on the VPS | yes | no | none |

**O4. The two keys.**

| Key | Signs | Compromise allows | Loss costs |
|---|---|---|---|
| APK key `notif-apk.p12` | the APK | signing APKs that Android accepts as Notif updates. Delivery still needs the repo or a manual sideload. The code then runs with Notif's granted permissions, including Health Connect reads. | uninstall and reinstall Notif, log in again, re-grant Health Connect (~5 min). `allowBackup=false`, so app data is gone anyway. |
| Index key `repo-index.p12` | `entry.jar` | signing a forged index, which only matters if the attacker also serves from the repo host. It cannot replace Notif without the APK key (F6). It can hide updates or offer other apps. | remove the repo on the phone and re-add it with the new fingerprint (~2 min) |

Root on the VPS reaches both keys, and it already reaches all Notif data and the Health Connect exports.
What a full compromise adds is code execution on the phone. Keeping the APK key on the laptop would
remove that, at the cost of a manual signing step for every release; I don't recommend it for a
single-user app.

Rotating the index key means re-adding the repo on the phone. Rotating the APK key can use
`apksigner rotate`, which writes a lineage file. The rotated key applies from API 33, or from API 28
with `--rotation-min-sdk-version 28` [a-apks]. For one phone, a reinstall is simpler. Both keys use a
validity of 10000 days; Android recommends at least 25 years [a-sign].

## Recommendation

1. **Build: option B.** A GHA workflow that runs only on `workflow_dispatch`, guarded by `if: github.ref == 'refs/heads/master'` and pinned to `ubuntu-24.04`. It builds an arm64-only release APK, which carries the runner's throwaway debug signature, and uploads it as an artifact kept for 7 days. B never puts a RAM or CPU spike next to production, never runs third-party build code on the production host, and needs no NDK work. This departs from "build on the VPS". The VPS *can* build: it is x86, and 8 GB is enough once the build container is capped at 5 GB. B is simply the better trade. A is the documented fallback: the publish half below is the same, and only the source of the unsigned APK changes. Confidence that B beats A: ~75%. The deciding question is whether a dependency on GitHub is acceptable.
2. **Sign and publish on the VPS** with `notif-apk publish`, a systemd oneshot. With a read-only PAT it fetches the newest successful dispatch run on master. It then:
   a. Requires `head_sha` to be reachable from `origin/master`, caps the artifact at 100 MB, and requires versionCode to be higher than the newest published one; an equal code from the same commit is a no-op.
   b. Re-signs inside a `--network none` container (apksigner discards the debug signature, F12). `apksigner verify --print-certs` must match the certificate SHA-256 committed in git, and `zipalign -c -P 16 4` must pass.
   c. Prunes `repo/` to the newest 3 APKs and runs `fdroid update`.
3. **Keys** live in `/etc/notif/fdroid/` (root, 0700; files 0600). Their passwords sit in `fdroid.env` and reach fdroid through `{env:}`. That keeps `config.yml` and `metadata/` free of secrets, so they go in git under `deploy/fdroid/`. Neither key is ever mounted into the backend container or sent to GitHub. Both keystores and passwords get an offline backup, and both public fingerprints are committed. `repo/status/*.json` is public by design (it records the command line), so no secret is ever passed as an argument.
4. **Versioning.** versionCode is `git rev-list --count` of the built commit. It always increases, because every new master commit has the old tip as an ancestor, so the set of commits it reaches only grows. versionName stays the pubspec value. `build.gradle` should fail instead of falling back to `1` (F5). Set `archive_older: 0` and keep 3 APKs.
5. **Hosting.** Serve `https://fdroid.lcenzo.com/repo`. Caddy mounts only `repo/`, read-only. Index files get `no-cache`; APKs, whose names include the versionCode and which are never overwritten, get `immutable`.
6. **Trigger.** Luka starts the build from the Actions tab ("Run workflow") or with `gh workflow run apk.yml --ref master`. Then `ssh vps notif-apk publish` runs in Phase 1; Phase 2 replaces it with a 15-minute timer. It is kept out of `deploy.sh`, which would otherwise gain a GitHub-dependent failure mode.

The update flow then runs:

1. A pull request merges as usual.
2. Luka triggers `apk.yml`, and about 5 min later the artifact is ready.
3. `notif-apk publish` runs: fetch, verify, sign, `fdroid update`.
4. Cloudflare passes the uncached index files straight through and edge-caches the immutable APK.
5. F-Droid on the phone sees the new `entry.jar` on a manual refresh, or within about 4 h, and offers the update.

```yaml
on: workflow_dispatch                       # never on push or pull_request
permissions: { contents: read }
jobs:
  apk:
    if: github.ref == 'refs/heads/master'
    runs-on: ubuntu-24.04
    defaults: { run: { working-directory: frontend } }
    steps:
      - uses: actions/checkout@v6
        with: { fetch-depth: 0 }            # rev-list --count needs full history
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '3.44.0', channel: stable, cache: true }
      - run: flutter build apk --release --target-platform android-arm64 --build-number "$(git rev-list --count HEAD)" --dart-define=API_URL=https://notif.lcenzo.com/api/v1 --dart-define=GIT_HASH="${GITHUB_SHA::7}"
      - uses: actions/upload-artifact@v7
        with: { name: notif-apk, path: frontend/build/app/outputs/flutter-apk/app-release.apk, retention-days: 7 }
```

```caddy
fdroid.lcenzo.com {
	tls {$FALLBACK_TLS_CERT} {$FALLBACK_TLS_KEY}
	root * /srv/fdroid                      # compose: /srv/notif-fdroid/repo:/srv/fdroid/repo:ro
	@index path /repo/entry.jar /repo/entry.json /repo/index-v1.jar /repo/index-v1.json /repo/index-v2.json /repo/diff/* /repo/index.html /repo/index.png
	header @index Cache-Control "no-cache"
	@apk path *.apk
	header @apk Cache-Control "public, max-age=31536000, immutable"
	file_server
}
```

`config.yml` needs only `repo_url`, `repo_name`, `repo_description`, `archive_older: 0`,
`repo_keyalias`, `keystore: /keys/repo-index.p12`, and `keystorepass`/`keypass: {env: FDROID_KS_PASS}`.
Here `/keys` is `/etc/notif/fdroid`, mounted read-only into the signer container.

## Phased plan

1. **Phase 0: app prerequisites** (one frontend PR).
   a. Set a final `applicationId` and namespace (Q3) and move `MainActivity.kt` to match.
   b. Make `build.gradle` fail when `flutter.versionCode` is missing. Raise `org.gradle.jvmargs` from 1536M to 4G, because R8 in release builds may exceed 1.5 GB (*inference*; the template uses 8G).
   c. Keep the debug signing placeholder for release; the VPS re-signs.
   d. Coordinate the package name with the Health Connect plan, since Health Connect grants are tied to the package.
2. **Phase 1: the milestone.** Manual, end to end.
   a. Generate both keys inside the signer image on the VPS: the index key with `fdroid init --keystore /keys/repo-index.p12 --repo-keyalias notif-repo`, the APK key with `keytool -genkeypair -storetype pkcs12 -keyalg RSA -keysize 4096 -validity 10000`. Back both up and commit the fingerprints.
   b. Add `deploy/fdroid/` (Dockerfile, `config.yml`, `metadata/`, `notif-apk`) and `.github/workflows/apk.yml`.
   c. Add the Caddy block, the compose mount and the DNS record.
   d. Dispatch a build and publish it. On the phone, add the repo by scanning the QR in `index.html`, or by opening `https://fdroid.lcenzo.com/repo?fingerprint=<sha256>`, then install.
   e. Exit criterion: after a trivial commit, a second dispatch shows up as an update after one refresh.
3. **Phase 2: hardening.**
   a. A 15-minute systemd timer for `publish`, bounded and idempotent.
   b. `gh attestation verify --signer-workflow LCEnzo/Notif/.github/workflows/apk.yml --source-ref refs/heads/master` before signing.
   c. A key-restore drill.
   d. A section in `vps_host.md`.
4. **Phase 3: optional.** Option A as a fallback. Its image is `deploy/android-build/Dockerfile`: `FROM ghcr.io/cirruslabs/flutter:3.44.0`, plus `sdkmanager "ndk;28.2.13676358"` and whatever else the first build downloads. Named volumes hold the Gradle and pub caches. It runs as `docker run --rm --memory 5g --cpus 3` from a manual `notif-apk build`, and feeds the same `publish`. The self-hosted runner from `TODO.md` is the other route.

## Risks

| Risk | Mitigation |
|---|---|
| Cloudflare caches `entry.jar` for 2 h (F3). Updates stay invisible, or the client sees a hash mismatch against the uncached `index-v2.json`. | Explicit `Cache-Control` per file, as in the snippet. Check with `curl -I` for `cf-cache-status`. |
| A missing `--build-number` yields versionCode 1 (F5). | The Gradle build fails without it, and publish refuses any code not higher than the last. |
| Shipping `com.example.notif`. The package name is permanent: renaming later means a reinstall and re-granting Health Connect. | Phase 0 settles it before the first install. |
| A rewrite of master history lowers versionCode, and Android refuses the downgrade (F6). | Never force-push master. Publish refuses any code ≤ the last. |
| Republishing the same versionCode with different bytes, while the old APK is still cached at the edge. | Publish never overwrites an existing APK file. |
| apksigner 35.0.2 might align to 4 KB, which matters only on phones with 16 KB memory pages (F12). | The `zipalign -c -P 16` check fails loudly; the fix is to use build-tools 36 apksigner. |
| Cloudflare bot protection challenges the F-Droid client, which is not a browser. | Test from the phone in Phase 1. If needed, add a skip rule for this host. |
| GitHub becomes unavailable or changes the free tier, or the repo goes private (2 vCPU / 8 GB, metered). | Fall back to option A; only the APK source changes. |
| The PAT expires. | Publish fails with a clear message; keep a calendar reminder. |
| A key is lost. | Offline backups. Even without them, recovery is cheap for one phone (O4). |
| Option A only: an OOM kill or CPU contention degrades production. | Container memory and CPU caps, `nice`, and building off-peak. |

## Open questions for Luka

1. Is depending on GitHub for builds acceptable (B)? Or should building stay on the VPS as you first framed it (A)? A costs a 3-5 GB RAM spike and 4-6 GB of disk.
2. Which hostname: `fdroid.lcenzo.com` or `notif.lcenzo.com/fdroid`? Does a wildcard DNS record exist, and does the origin cert cover `*.lcenzo.com`? Check with `openssl x509 -noout -ext subjectAltName`.
3. What should the final `applicationId` be? I suggest `com.lcenzo.notif`.
4. Is the phone arm64, and is it the only device?
5. What is the VPS's actual headroom? Please run `nproc; free -m; df -h /; docker system df`, because the repo has no live numbers.
6. Where do the key backups go: the password manager, an offline drive, or both?
7. Is a polling timer worth it, or is `ssh vps notif-apk publish` after each dispatch enough?
8. Is Cloudflare Bot Fight Mode or a similar challenge enabled on `lcenzo.com`?
9. Is the repo for Notif only, or for other apps too? That decides `repo_name`.
10. Should the repo require HTTP basic auth? The client accepts repo credentials (`RepoAdder.kt`), and Caddy `basic_auth` takes about 3 lines. The APK is built from the public source plus the API URL, so I see little to hide; the default is no auth.
